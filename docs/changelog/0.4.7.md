> Data rilascio: 20 marzo 2026

- Download senza timeout globale (download "zombie")

## 🟠 Fix 1: Download Senza Timeout Globale

### Il Problema

`DownloadService.attemptDownload()` non aveva **nessun timeout** sulla richiesta HTTP:

```typescript
// ❌ PRIMA — nessun timeout, nessuna protezione stall
const response = await axios({
    url,
    method: 'GET',
    responseType: 'stream',
    // timeout: ??? — assente!
});
```

**Scenari rischiosi:**
- Un server che non risponde mai → la connessione resta aperta **indefinitamente**
- Un server che invia 1 byte ogni 50 secondi → il download non termina mai
- Uno slot nella coda download (`QueueService`) resta occupato per sempre → blocca la coda

### La Soluzione: Doppio Timeout

#### 1. Connection Timeout (30s)
Timeout sulla connessione HTTP iniziale — se il server non risponde entro 30 secondi, Axios lancia `ECONNABORTED`:

```typescript
const response = await axios({
    url,
    method: 'GET',
    responseType: 'stream',
    timeout: 30_000, // ← v0.4.7
});
```

#### 2. Stall Detection (60s)
Timer che si resetta ad ogni chunk ricevuto. Se non arrivano dati per 60 secondi, il download viene abortito:

```typescript
let stallTimer: ReturnType<typeof setTimeout> | null = null;

const resetStallTimer = () => {
    if (stallTimer) clearTimeout(stallTimer);
    stallTimer = setTimeout(() => {
        response.data.destroy();  // Chiude lo stream
        reject(new Error('DOWNLOAD_STALLED'));
    }, 60_000);
};

response.data.on('data', (chunk: Buffer) => {
    loaded += chunk.length;
    resetStallTimer();  // ← Reset ad ogni chunk
});
```

| Scenario | Timeout | Errore generato |
|----------|:-------:|:---------------:|
| Server non risponde | 30s | `DOWNLOAD_TIMEOUT` |
| Server blocca durante trasferimento | 60s inattività | `DOWNLOAD_STALLED` |
| Nessun problema | ∞ | — |

Entrambi gli errori **non vengono retryati** (sono da considerarsi permanenti per quel tentativo).

### Bonus: Backoff Esponenziale

Il retry era a backoff fisso (1s). Ora usa backoff esponenziale:

```diff
-await new Promise(resolve => setTimeout(resolve, 1000));
+await new Promise(resolve => setTimeout(resolve, 1000 * Math.pow(2, i)));
```

| Tentativo | Attesa prima |  Attesa dopo |
|:---------:|:----------:|:----------:|
| 1 | 1s | 1s |
| 2 | 1s | 2s |
| 3 | 1s | 4s |

## 🟠 Fix 2: `window.location.reload()` come Gestione Stato

### Il Problema

Due punti in `SettingsModal.tsx` forzavano un **reload dell'intera applicazione**:

```typescript
// ❌ Dopo reset download history (riga 51)
await window.api.resetDownloadHistory();
window.location.reload();

// ❌ Dopo import OPML (riga 205)
toast.show(t('settings.import_success', { count: res.count }), 'success');
setTimeout(() => window.location.reload(), 1500);
```

**Conseguenze:**
- Perdita di tutto lo stato Zustand (feed corrente, progresso download, filtri)
- Se c'era un download in corso, veniva interrotto senza cleanup
- L'utente perdeva il contesto di navigazione
- Anti-pattern in un'app Electron con state management

### La Soluzione

#### Reset Database
```diff
-window.location.reload();
+// v0.4.7 — update state without reloading
+setArchiveStats({ totalFiles: 0, totalPodcasts: 0, oldestDate: null, newestDate: null });
+toast.show(t('settings.reset_success', 'Download history cleared.'), 'success');
```

Lo stato `archiveStats` viene azzerato localmente + toast di conferma. I download (`downloads`) si aggiornano via push event `DOWNLOADS_UPDATED` già implementato.

#### Import OPML
```diff
-setTimeout(() => window.location.reload(), 1500);
+// v0.4.7 — feeds auto-update via onFeedsUpdated push event
```

L'handler IPC di `IMPORT_OPML` già chiama `pushEvent(mainWindow, CH.FEEDS_UPDATED, feeds)` dopo l'import. La sidebar riceve automaticamente i nuovi feed tramite `onFeedsUpdated`.
