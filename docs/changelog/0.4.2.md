# 🛡️ v0.4.2 — "Batch Integrity"

> Data rilascio: 20 marzo 2026

Questa release risolve una **criticità gravissima** identificata nell'analisi del codice: una race condition nel sistema di tracking dei download batch che causava notifiche premature o mancanti.

---

## 🔴 Fix Criticità Gravissima: Race Condition nel Batch Tracker

### Il Problema

Il batch tracker era un **oggetto mutabile globale** in `ipc.ts`:

```typescript
// ❌ PRIMA (v0.4.0–v0.4.1)
let batchTracker = { total: 0, completed: 0, active: false };
```

Il flusso era:
1. Ogni chiamata `START_DOWNLOAD` → `batchTracker.total++` (sincrono, nell'handler IPC)
2. Ogni download completato → `batchTracker.completed++` (asincrono, nel `finally` del task in coda)
3. Check: `if (completed >= total && active)` → notifica OS + reset

#### Scenario di Race Condition

Quando l'utente clicca **"Scarica Tutto"** per 10 episodi:

```
Tempo  │ Evento                      │ total │ completed │ Bug?
───────┼─────────────────────────────┼───────┼───────────┼──────
  0ms  │ START_DOWNLOAD ep1          │   1   │     0     │
  1ms  │ START_DOWNLOAD ep2          │   2   │     0     │
  5ms  │ ep1 download completa       │   2   │     1     │
  6ms  │ START_DOWNLOAD ep3          │   3   │     1     │
 10ms  │ ep2 download completa       │   3   │     2     │
 12ms  │ START_DOWNLOAD ep4          │   4   │     2     │
```

Ma con concurrency alta e CDN veloci, poteva succedere:

```
Tempo  │ Evento                      │ total │ completed │ Bug?
───────┼─────────────────────────────┼───────┼───────────┼──────
  0ms  │ START_DOWNLOAD ep1          │   1   │     0     │
  3ms  │ ep1 download completa       │   1   │     1     │ ⚠️ 1>=1
       │ → NOTIFICA PREMATURA!       │   0   │     0     │ 🔴 RESET
  5ms  │ START_DOWNLOAD ep2          │   1   │     0     │ ← ricomincia
  6ms  │ START_DOWNLOAD ep3          │   2   │     0     │
 ...   │ (i restanti 7 non verranno  │       │           │
       │  mai conteggiati)           │       │           │
```

**Effetti visibili:**
- Notifica OS "Download completato: 1 file scaricato" invece di 10
- La barra di progresso si resettava prematuramente
- I download rimanenti non venivano tracciati

### La Soluzione: Classe `BatchTracker` con Seal Window

Creata la classe `BatchTracker` in `electron/services/BatchTracker.ts` che implementa una strategia di **stabilizzazione temporale**:

```typescript
// ✅ DOPO (v0.4.2)
const batchTracker = new BatchTracker();
```

#### Come funziona

```
track()    → registra un download, resetta il timer di sigillatura
             (il batch NON può completarsi per 200ms dopo l'ultima track())

complete() → marca un download come completato.
             Ritorna il totale SOLO quando:
             ✅ Il batch è "sigillato" (nessuna track() da 200ms)
             ✅ Tutti i download registrati sono completati
             Altrimenti ritorna null.

reset()    → azzera tutto (usato da STOP_BATCH)
```

#### Perché funziona

Il "seal window" di 200ms garantisce che:

1. **Tutti i `START_DOWNLOAD` IPC vengono processati** prima che qualsiasi `complete()` possa innescare la notifica
2. Il timer si **resetta ad ogni `track()`**, quindi bursts di download rapidi non sfondano la finestra
3. Solo **dopo** che l'ultimo download è stato accodato (e sono passati 200ms senza nuove `track()`), il batch si "sigilla" e `complete()` può ritornare il totale
4. Se l'utente avvia un secondo batch dopo il primo, il tracker è già resettato e funziona correttamente

#### Scenario corretto post-fix

```
Tempo  │ Evento                      │ total │ sealed │ complete()
───────┼─────────────────────────────┼───────┼────────┼───────────
  0ms  │ track() ep1                 │   1   │ false  │
  3ms  │ ep1 download completa       │   1   │ false  │ → null ✅
  5ms  │ track() ep2 (timer reset)   │   2   │ false  │
  6ms  │ track() ep3 (timer reset)   │   3   │ false  │
 ...   │ track() ep4–10              │  10   │ false  │
210ms  │ (200ms dopo ultima track)   │  10   │ TRUE   │
 ...   │ download completano...      │  10   │ true   │ → null
 ...   │ ultimo download completa    │  10   │ true   │ → 10 ✅
```

#### Test chiave — Riproduzione esatta della race condition:

```typescript
it('should NOT fire premature completion when downloads finish before all are queued', () => {
    tracker.track();                   // 1° download accodato
    const result = tracker.complete(); // 1° download completa subito!
    expect(result).toBeNull();         // 🚫 NON deve scattare la notifica

    tracker.track(); tracker.track();  // altri accodati...
    tracker.track(); tracker.track();
    vi.advanceTimersByTime(200);       // sigillatura

    tracker.complete(); // 2
    tracker.complete(); // 3
    tracker.complete(); // 4
    const final = tracker.complete();  // 5
    expect(final).toBe(5);            // ✅ Ora sì, tutti completati
});
```

## ⚠️ Note Tecniche

### Perché 200ms di debounce?

- Le chiamate `START_DOWNLOAD` IPC arrivano sequenzialmente dal renderer via `forEach`
- Su un sistema tipico, 100 chiamate IPC sequenziali richiedono < 50ms
- 200ms fornisce un margine di sicurezza 4x anche su sistemi sotto carico
- Il delay non impatta l'UX perché riguarda solo il **timing della notifica finale**, non la velocità dei download

### Perché non usare `queue.on('idle')`?

- `PQueue.idle` scatta quando la coda è vuota E non ci sono task in esecuzione
- Ma la coda potrebbe svuotarsi temporaneamente tra due burst di `add()` → falso positivo
- Il seal window è più robusto perché traccia il flusso di **registrazione** (frontend), non di esecuzione
