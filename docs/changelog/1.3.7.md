# Changelog v1.3.7

**Data:** 29 maggio 2026

## Criticità medie — correttezza motore e sicurezza (M1–M4)

Primo blocco della risoluzione delle criticità **medie** dell'audit del 29 maggio 2026.

### M1 — Collisione del file `.part` su download concorrenti

Il controllo anti-collisione aggiungeva il suffisso `_2`, `_3` solo se un file **già
completato** esisteva su disco. Due download concorrenti che risolvevano allo stesso
nome (es. lo stesso episodio avviato due volte) non vedevano alcun file completo e
scrivevano entrambi sullo **stesso `.part`**, corrompendosi a vicenda.

* Introdotto un set `reservedTargets` dei path già rivendicati dai download in volo.
* La selezione del nome ora usa `fs.existsSync` (sincrona) e controlla **sia** i file su
  disco **sia** i path riservati: la rivendicazione è quindi atomica e nessun secondo
  handler può scegliere lo stesso path.
* Path rilasciato su tutte le uscite del task: completamento, errore e annullamento
  prima dell'apertura dello slot di coda.

### M2 — Validazione dei path negli IPC `OPEN_FOLDER` / `OPEN_ARCHIVE_FILE`

`shell.openPath` / `shell.showItemInFolder` ricevevano path dal renderer senza
validazione.

* `OPEN_FOLDER`: apre **solo** una directory reale ed esistente (`fs.stat` +
  `isDirectory`); ignora file arbitrari o path inesistenti.
* `OPEN_ARCHIVE_FILE`: ora sanitizza **anche** il `filename` (non solo il titolo
  podcast) e verifica che il path risolto resti dentro `baseDir` — difesa contro un
  `..` di traversal in una voce d'archivio malformata.

### M3 — Tolleranza di integrità troppo larga (1% → 0,1%)

La verifica post-download accettava uno scarto fino all'**1%** rispetto a
`Content-Length`: su un file da 100 MB significava tollerare ~1 MB mancante. Ridotta a
**0,1%**: un trasferimento corretto combacia esattamente, la tolleranza residua assorbe
solo quirk di byte finali, non un download troncato.

### M4 — Cap dimensione risposta feed + guardia XXE esplicita

* `FeedService`: aggiunti `maxContentLength` / `maxBodyLength` (15 MB) — un feed è
  piccolo; questo impedisce a un server ostile di streammare un body illimitato in
  memoria.
* Nuovo helper `electron/utils/xmlSafety.ts` (`hasDangerousDoctype`): rifiuta a monte
  qualunque XML che dichiari un `DOCTYPE` con definizioni `<!ENTITY ...>` (vettore XXE /
  "billion laughs"). Applicato sia al parsing dei feed sia all'import OPML. I parser
  sottostanti non espandono entità esterne: la guardia rende la policy **esplicita**
  anziché affidarsi al default.
